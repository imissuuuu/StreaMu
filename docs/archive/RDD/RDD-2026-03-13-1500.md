## 2. 詳細仕様

### FR-1: SearchScreen
- **入力処理**: KEY_A(曲選択/再検索/一時停止切替)、KEY_DDOWN/DUP(リスト移動)、KEY_DRIGHT/DLEFT(スクロール)
- **描画(top)**: UIRenderer::draw_top_screenのSTATE_SEARCH部分を移管
- **描画(bottom)**: UIRenderer::draw_bottom_screenのSTATE_SEARCH部分を移管
- **特殊処理**: 先頭に「[ 検索 ]」ボタン(SEARCH_BTN)を挿入するロジック
- **外部依存**: `start_playback`ラムダ、`YouTubeAPI`、ソフトウェアキーボード呼び出し
- **戻り値アクション**: `"trigger_search_keyboard"`, `"trigger_playback:<index>"`, `"trigger_pause_toggle"` 等をmain.cppに返す

### FR-2: PlaylistsScreen
- **入力処理**: KEY_A(プレイリスト選択→PlaylistDetailへ遷移)、KEY_DDOWN/DUP(リスト移動)
- **描画(top)**: UIRendererの既存top描画を流用
- **描画(bottom)**: プレイリスト一覧表示(名前 + トラック数)
- **戻り値アクション**: `"trigger_playlist_detail:<index>"` をmain.cppに返す

### FR-3: PlaylistDetailScreen
- **入力処理**: SearchScreenとほぼ同構造(KEY_A=曲選択、DPad=移動/スクロール)
- **描画**: SearchScreenと同構造(2行レイアウト: タイトル + メタデータ)
- **特殊処理**: シャッフルキュー生成、active_playlist設定
- **戻り値アクション**: `"trigger_playback:<index>"`, `"trigger_pause_toggle"` 等

### FR-4: rebuild_buttons修正
- `HomeScreen::update()`内でのみ`rebuild_buttons()`を呼ぶ
- `playing_id`の変更を検知する仕組み(前フレームの値を保持して比較)を導入
- `draw_bottom()`では既にビルド済みのボタンリストをそのまま描画する

### FR-5: ScreenManagerへの統合
- main.cppの`main()`内で`SearchScreen`、`PlaylistsScreen`、`PlaylistDetailScreen`をadd_screen
- `STATE_SEARCH/PLAYLISTS/PLAYLIST_DETAIL`時のif/elseブロックを、ScreenManager経由の`update()`/`draw_top()`/`draw_bottom()`呼び出しに置き換え
- main.cppの描画ループで`screen_mgr.draw_top()`/`screen_mgr.draw_bottom()`を使う

## 3. UI/UX考慮事項

- **見た目の変更なし**: 描画コードはUIRendererからそのまま移植。色・フォントサイズ・レイアウトは一切変えない
- **操作の変更なし**: ボタン割り当て・D-Padの挙動・タッチ操作は現行と同一
- **ポップアップとの共存**: ポップアップ(5種)はmain.cppに残るため、`previous_state`を正しくセットしてからScreenManagerの画面遷移を行う

```
[main.cpp 描画フロー(リファクタリング後)]

begin_top_screen()
  if (bg_state is Screen管理対象)  → screen_mgr.draw_top()
  else                            → renderer.draw_top_screen()  ← 接続待ち画面等

begin_bottom_screen()
  if (bg_state is Screen管理対象)  → screen_mgr.draw_bottom()
  else                            → renderer.draw_bottom_screen()

if (is_popup)
  renderer.draw_popup_overlay()   ← ポップアップはmain.cppに残る

end_frame()
```

## 4. 追加設計情報

### Screen間のデータ共有パターン
- 各ScreenはAppContext参照を`update()`で受け取り、状態を読み書きする
- 描画はRenderContext(AppContextのスライシングコピー)を受け取る(読み取り専用)
- `start_playback`等の複雑な処理はmain.cppに残し、Screenからはアクション文字列を返す

### スレッド安全性
- Screen内で`ctx.lock`を使う場合、既存と同じ`LightLock_Lock`/`Unlock`パターンを厳守
- 描画関数(`draw_top`/`draw_bottom`)はRenderContextのコピーを受け取るため、ロック不要

### 破壊順序
- exit時: `screen_mgr.clear()` → `g_renderer_ptr.reset()` → `g_ui_mgr_ptr.reset()` → ハードウェアExit
- 新しいScreenが追加されてもこの順序は変わらない(ScreenManagerが全Screenを管理)

### 非機能要件
| ID | 内容 |
|----|------|
| NFR-1 | 動作の完全維持: リファクタリング前後で見た目・操作・音声再生の挙動が一切変わらない |
| NFR-2 | 破壊順序の維持: C++オブジェクト破棄 → ハードウェアExit の順序を崩さない |
| NFR-3 | スレッド安全性の維持: LightLockによる排他制御パターンを維持 |
| NFR-4 | ポップアップとの互換: ポップアップ5種はmain.cppに残り、previous_state等を正しく参照できる |

### 対象外
- ポップアップ5種の移行
- 起動時接続待ち画面の移行
- 新機能追加・UI変更
- include/とsource/のヘッダ配置整理
