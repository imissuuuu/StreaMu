## 2. 詳細仕様

### FR-1: native Opus/WebM 取得確認
- 入力: YouTube video ID。
- 処理: `yt-dlp` で `bestaudio[acodec*=opus]` 相当の format を選択する。
- 出力: Opus 音声 format が存在する場合、`webm_dash` / `opus` / `48000 Hz` などの取得情報が得られる。
- 取得できない場合は PoC 対象外として扱い、AAC や MP3 への自動変換 fallback は行わない。

### FR-2: Opus info API
- 入力: `GET /api/opus-info?i=<video_id>`。
- 処理: video ID を検証し、`yt-dlp` で Opus format 情報を抽出する。
- 出力: JSON で codec/container/bitrate/sample rate/channel/direct URL 有無/fragments 数を返す。
- 失敗時: invalid ID は `400`、Opus format 不在または抽出失敗は `502` を返す。

### FR-3: Opus stream API
- 入力: `GET /stream_opus?i=<video_id>`。
- 処理: Opus format の direct URL または fragment 情報を使い、サーバーが bytes を中継する。
- 出力: `audio/webm` または検証で妥当と判断した media type の StreamingResponse を返す。
- 範囲外: サーバー側で `.ogg`, `.mp3`, `.aac` などへ変換しない。

### FR-4: 3DS decode / demux 方針検証
- 入力: サーバーから取得した Opus/WebM byte stream、または同等の小さな local test sample。
- 処理: 3DS 側で WebM container と Opus frame を扱えるか、またはサーバー側で再エンコードなしに WebM Opus を Ogg Opus へ remux して 3DS 側を `opusfile` に寄せられるかを確認する。
- 出力: 実装可能性、必要な追加依存、最小PoC手順を文書化する。
- 実機再生まで到達できる場合は、隠し操作または開発専用経路で音が鳴ることを確認する。

### FR-5: 既存経路の保持
- 入力: 通常の検索・再生操作。
- 処理: 既存の AAC Direct / MP3 Proxy 経路は今回の PoC では変更しない。
- 出力: 既存の通常再生、Settings 表示、config 保存形式に不要な差分が出ない。

### FR-6: 判断材料の文書化
- 入力: `yt-dlp` format 確認、サーバー API 検証、3DS decode 調査または実機結果。
- 処理: PoC 結果を `docs/POC/` に記録する。
- 出力: Opus Direct を次フェーズへ進めるか、代替案に戻すかを判断できる。

## 4. 追加設計情報
- 既存サーバーは `server/proxy.py` で Starlette を使い、`yt-dlp` と `urllib` による direct URL 中継実績がある。
- `yt-dlp 2026.03.17` で確認した代表動画では、AAC/m4a と Opus/webm は取得でき、Vorbis/Ogg は取得できなかった。
- Opus は YouTube から再エンコードなしで取れる可能性が高いため、FFmpegless / AAC-free の本命候補として扱う。
- `docs/POC/3ds-audio-reference-notes.md` は、3DS 側で重いコンテナ処理を持たず、サーバー側で軽い整形を行う方針を既に採っている。AAC PoC では MP4 parsing を 3DS 側で避け、server transmux 後の ADTS を 3DS が decode する形にした。
- `docs/POC/ffmpegless-audio-poc.md` では、YouTube の `m4a_dash` を server-side transmux して ADTS にし、3DS 側では AAC ADTS decoder のみに絞る方式が PASS している。この前例を Opus でも踏まえる。
- `docs/POC/vorbis-decoder-poc.md` と `docs/POC/vorbis-playback-poc.md` では、Ogg Vorbis の decoder / playback は成立したが、YouTube から Ogg Vorbis を直接取る経路や server-side YouTube→Vorbis 変換は未実装・対象外だった。
- `C:\dev\research\3ds-audio-refs\ctrmus` は 3DS 上で Opus 再生実績があり、依存として `3ds-libopus` / `3ds-opusfile` / `3ds-libogg` を使っている。ただし `ctrmus` 本体は GPLv3 のためコードコピー禁止。
- `C:\devkitPro\examples\3ds\audio\opus-decoding` は libopusfile を使った 3DS Opus 再生サンプルで、O3DS でも filesystem から threaded streaming decode できる例として扱う。
- devkitPro package 実物確認済み: `3ds-libogg` / `3ds-libopus` / `3ds-opusfile` / `3ds-pkg-config` は導入済み。
- `3ds-libopus 1.4-1` と `3ds-opusfile 0.11-1` は pacman package metadata 上 `Licenses: BSD`。`opus.h` と `opusfile` 同梱 `COPYING` でも BSD-style / BSD-3-Clause 条件を確認済み。
- `3ds-libogg` は `C:\devkitPro\portlibs\3ds\licenses\3ds-libogg\COPYING` で BSD-3-Clause 条件を確認済み。
- devkitPro Opus example は `op_read_stereo()` で 48 kHz stereo PCM を得て NDSP に渡している。StreaMu 側でも最初は `opusfile` API を優先候補にする。
- 注意点: `opusfile` は `.opus`、つまり Ogg Opus stream を扱うライブラリであり、YouTube の native Opus は通常 `webm_dash`。WebM demux を3DS側で行うか、サーバー側で再エンコードなしの WebM→Ogg Opus remux が可能かを System Design で検討する。
- Opus 公式情報では reference implementation は 3-clause BSD とされ、Xiph 側の特許許諾もある。ただし第三者IPRの注意書きは残るため、公式release前にライセンスレビューを通す。
