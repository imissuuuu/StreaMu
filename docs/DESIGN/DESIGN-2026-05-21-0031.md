# システム設計書 - Opus Performance Instrumentation
**RDD:** `RDD-2026-05-21-0031.md`  
**作成日:** 2026-05-21

## 1. 全体方針
- Opus Direct の動作を変えず、状態遷移時だけ低頻度の計測ログを追加する。
- 3DS側は SD カード上の `sdmc:/3ds/StreaMu/opus_perf.log` に追記する。
- サーバー側は既存 `add_log()` を使い、dashboardで見える形にする。
- 本実装では最適化そのものは行わない。

## 2. 新規ファイル
なし。

## 3. 既存ファイルの変更
### `source/network/youtube_api.cpp`
- Opus Ogg stream中だけ有効な小さな計測状態を追加する。
- `start_streaming()` 開始時に `stream request start` を記録する。
- `StreamingWriteCallback()` で first byte と 16KB到達を1回だけ記録する。
- `start_streaming()` 終了時に success/fail と累計bytesを記録する。

### `source/main.cpp`
- Opus Direct 再生開始時に端末側計測ログを初期化する。
- decoder open開始/結果を記録する。
- `has_started_playing()` が初めて true になった時点を記録する。

### `server/proxy.py`
- `opus_ogg_generator()` 内で `time.monotonic()` を基準にする。
- WebM上流first byte、初回Ogg page、16KB送信、終了時summaryを記録する。
- 例外時も既存エラーログを維持する。

## 4. 各機能の詳細設計
### FR-1 / FR-3: 3DS側計測
ログ形式:
```text
[opus-perf] +1234ms event-name detail
```

経過時間は Opus Direct の `start_streaming()` 開始からの差分とする。ログファイルを開けない場合は何もしない。

### FR-2: サーバー側計測
ログ例:
```text
Opus perf: upstream first byte +321ms bytes=16384
Opus perf: first ogg page +420ms bytes=47
Opus perf: sent 16KB +650ms pages=19
Opus perf: finished +123456ms sent=3667561 pages=10655
```

### FR-4: 回帰防止
- `OPUS_STREAM_START_BYTES` は変更しない。
- Ogg page の内容・粒度は変更しない。
- decode buffer数や `update()` の処理量は変更しない。

## 5. 状態設計
### 3DS側
- `youtube_api.cpp` 内にファイルローカルの計測状態を持つ。
- `main.cpp` 内に `audio started` の重複ログ防止フラグを持つ。

### サーバー側
- `opus_ogg_generator()` ローカル変数として `perf_start`, `first_page_logged`, `sixteen_k_logged`, `page_count` を持つ。

## 6. 実装順序
1. `source/network/youtube_api.cpp` に受信側計測ログを追加する。
2. `source/main.cpp` に decoder/audio started 計測ログを追加する。
3. `server/proxy.py` にサーバー側計測ログを追加する。
4. `python -m py_compile server/proxy.py server/webm_opus_remux.py server/opus_probe.py`。
5. `make clean && make`。
6. 実機test:
   - Opus Direct 通常再生で `opus_perf.log` が生成される。
   - dashboard に Opus perf log が出る。
   - Opus Direct の通常再生が従来通り成功する。
   - AAC Direct / MP3 Proxy の通常再生に影響がない。
